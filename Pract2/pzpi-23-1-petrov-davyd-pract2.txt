3 ОПИС ВИКОНАНОЇ РОБОТИ

3.1 Загальні відомості про систему
Назва системи: Платформа Uber
Розробник: Uber Technologies Inc.
Призначення системи: Платформа для замовлення транспортних послуг (ride-hailing), доставки їжі (UberEats) та логістики. Мобільний додаток з'єднує водіїв та пасажирів у режимі реального часу. Ключовою складністю системи є динамічне ціноутворення, геопросторовий пошук та високе навантаження.

3.2 Архітектурний стиль системи
Архітектурний стиль: Мікросервісна архітектура (з еволюцією до Domain-Oriented Microservice Architecture - DOMA), Event-Driven Architecture.
Обґрунтування вибору: На початковому етапі розробки (2010 рік) система мала монолітну архітектуру, що дозволило швидко вийти на ринок. Проте зі стрімким зростанням бази користувачів моноліт перестав справлятися з навантаженням, а команди розробників заважали одна одній. Перехід на мікросервіси дозволив незалежно масштабувати та розгортати окремі компоненти (пошук водіїв, оплата, розрахунок маршруту), використовувати різні мови програмування (Go, Java, Python) та підвищити відмовостійкість.

3.3 Основні компоненти системи
Опис підсистем:
- Інтерфейс користувача: Нативні мобільні додатки для iOS та Android (окремо для водіїв і пасажирів), а також веб-додатки.
- API Gateway: Шлюз, який приймає всі запити від клієнтів, забезпечує авторизацію, маршрутизацію та rate limiting.
- Dispatch Service (Сервіс диспетчеризації): Ядро системи, що відповідає за знаходження відповідного водія для пасажира.
- Routing & ETA Service: Сервіс для розрахунку оптимального маршруту та орієнтовного часу прибуття (Estimated Time of Arrival) з урахуванням заторів.
- Payment Service: Рівень бізнес-логіки для обробки транзакцій та інтеграції з банківськими шлюзами.
- Рівень зберігання даних: Schemaless (власна БД над MySQL для інформації про поїздки), Apache Cassandra (для GPS-координат), Redis (кешування).

3.4 Взаємодія компонентів
Для синхронної комунікації між мікросервісами використовується протокол gRPC (поверх HTTP/2 з серіалізацією Protocol Buffers), що забезпечує мінімальну затримку та типізацію даних.
Для асинхронної взаємодії та логування подій використовується брокер повідомлень Apache Kafka. Наприклад, після завершення поїздки сервіс публікує подію в Kafka, яку асинхронно зчитують сервіси оплати, розсилки повідомлень та аналітики.

3.5 Масштабованість та надійність
- Механізми балансування: Зовнішні балансувальники навантаження (HAProxy) розподіляють трафік між API-шлюзами.
- Відмовостійкість: Паттерни Circuit Breaker (запобігання каскадним збоям) та Graceful Degradation.
- Реплікація: Дані дублюються між кількома географічно розподіленими дата-центрами за принципом Active-Active.
- Контейнеризація: Усі мікросервіси упаковуються в Docker-контейнери, для їх оркестрації та управління життєвим циклом використовується Kubernetes.

3.6 Використання засобів штучного інтелекту
Назва інструменту та версія: Google Gemini (Advanced).
Мета використання: Пошук актуальної технічної інформації щодо переходу Uber від мікросервісів до архітектури DOMA, генерація базового каркаса програмного коду для симуляції Dispatch Service (на мові Python).

4 ВИСНОВКИ

У результаті виконання практичного заняття було досліджено архітектуру масштабної платформи Uber. Визначено її мікросервісний (та подієво-орієнтований) архітектурний стиль. Проаналізовано взаємодію ключових компонентів за допомогою gRPC та Apache Kafka. Оцінено переваги (гнучкість, незалежне масштабування) та недоліки (мережеві затримки, складність моніторингу) мікросервісного підходу. Розглянуто новітній підхід DOMA (Domain-Oriented Microservice Architecture), який допомагає компанії управляти тисячами сервісів. Сформовано практичні навички архітектурного аналізу програмних систем.

10 class DispatchService:

17     def _calculate_distance(self, lat1, lon1, lat2, lon2):
18         # Спрощена формула розрахунку відстані (Евклідова відстань)
19         return math.sqrt((lat1 - lat2)**2 + (lon1 - lon2)**2)
20
21     def find_nearest_driver(self, passenger_lat, passenger_lon):
22         nearest_driver = None
23         min_distance = float('inf')
24
25         for driver in self.drivers:
26             if driver.is_available:
27                 distance = self._calculate_distance(
28                     passenger_lat, passenger_lon, driver.lat, driver.lon
29                 )
30                 if distance < min_distance:
31                     min_distance = distance
32                     nearest_driver = driver
33
34         if nearest_driver:
35             nearest_driver.is_available = False # Водій прийняв замовлення
36             return nearest_driver.driver_id
37         return None
